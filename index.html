01

변하는 것은 모델 하나가 아니라
소프트웨어의 판단 비용이다.

공개 발표

Jev는 텍스트 생성 대신 typed probabilistic decision을 반환한다.

TypeSafe는 이를 System One 모델로 설명하며, 비정형 상태를 받아 소프트웨어가 직접 사용할 수 있는 구조화된 판단과 확률을 반환하는 방식으로 제시한다.

공개 발표

오픈 구현은 이미 ‘생성 없이 option logits를 읽는’ 패턴을 재현하고 있다.

Qwen·Gemma 계열을 이용한 여러 독립 프로젝트가 shared-state prefill, one-pass option scoring, Jev-compatible API 같은 접근을 공개했다. 하지만 완전한 Jev 성능·경제성의 재현이 입증된 것은 아니다.

가설

판단의 한계비용이 낮아지면 AI 호출 수는 줄기보다 늘어날 수 있다.

relevant? duplicate? stale? enough evidence? retry? escalate? 같은 작은 의미 판단이 프로그램 내부의 평범한 분기처럼 사용될 수 있기 때문이다. 이 가설은 실제 워크로드에서 검증해야 한다.

Jev 같은 System One 모델과 빠르게 등장한 오픈 구현들은 새로운 가능성을 보여준다. 의미 판단이 충분히 싸고 빠르면, RAG의 중심은 ‘가장 비슷한 5개’를 찾는 것에서 ‘충분하고 모순을 설명할 수 있는 근거 집합’을 만드는 것으로 이동한다.

02

RAG는 가장 먼저
구조가 바뀔 수 있는 영역이다.

01범위 안에서 넓게 찾기scope · dense · sparse · filters
→
02명시적으로 판단relevance · evidence · time
→
03근거 집합 구성dedupe · conflict · coverage
→
04원문으로 검증id · version · ACL · span
→
05필요한 것만 추론answer · cite · abstain
기존 RAG의 실전 문제
재정의
0.82, 0.81, 0.80 — 비슷한 후보를 억지로 순위화
현재 evidence set에 ‘새로운 근거’를 더하는가?
상충 문서 중 하나가 높은 점수라서 살아남음
모순인가, 예외인가, 버전 차이인가, 권위 차이인가?
Top-K라서 관련 없는 것도 항상 K개 전달
0개도 정답. evidence sufficiency가 종료 조건.
중복 chunk가 context window를 소비
문장 유사도가 아니라 claim equivalence와 marginal value 평가

임베딩은 사라지지 않는다. 역할이 명확해진다. 정해진 범위 안에서 후보를 넓게 찾고, 값싼 semantic decision layer가 근거 집합을 구성하고, 원문 시스템이 그 근거를 검증한다.

rag-migrate

04

좋아 보이는 architecture가 아니라,
반증 가능한 성능 가설.

↑Evidence Recall필수 근거를 놓치지 않는가
↓Redundancy반복 context가 줄었는가
↑Conflict Capture상충 근거를 같이 잡는가
↓Unsupported Claims근거 없는 주장이 줄었는가
↔p95 / Cost운영 한계 안에 있는가

이 프로젝트는 Jev/OpenJev가 항상 더 좋다고 주장하지 않는다. 실제 baseline과 같은 corpus·query를 사용해 측정하고, 실패하면 기존 시스템을 유지하는 것이 원칙이다.
